# Accessibility and comfort

Design the visual stage and interactive controls as one experience. Canvas drawings alone are not an accessible interface. Use supported button, input and select nodes for essential actions so the player can expose semantic HTML controls and keyboard interaction.

Give every control a clear visible label and an unambiguous action. Do not communicate correctness, status or meaning by color alone. Pair color with text, shape, iconography or position. Keep text contrast high and use a readable body size. Avoid long blocks of tiny text.

Do not make hover the only way to reveal information. Ensure the lesson can be followed with keyboard-only input and on touch devices. Make targets large enough to activate comfortably. Keep input prompts, focus order and result feedback understandable.

For video-like scenes, use captions for speech, do not place essential information only in audio, and hold dense diagrams long enough to inspect. Do not use rapid flashing or strobing. Reduce unnecessary parallax, zoom and constant motion. When the player or runtime supports reduced-motion preferences, respect them; do not claim support if it has not been implemented and tested in that build.

Test at narrow viewport sizes, high zoom, and with Arabic or other right-to-left content when relevant. Check both the visual stage and the accessible control layer. Never sacrifice legibility for decorative density.\n
