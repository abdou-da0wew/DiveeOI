# Draft 10 — Autonomous Agent (autonomous AND manual, smart by default)

Source: design discussion on running DiveeOI as a long-running autonomous agent on free/small
LLMs (Zen free models, ≤1M context). Core principle agreed with the user: **the agent can be
autonomous AND manual — it is both — and smart by default.** Manual is just autonomous with a
human in the loop; every autonomy mechanism must degrade gracefully to manual control, and the
smart behavior must be the default, not an opt-in.

Everything below builds on the existing Effect-TS layer graph, the feature-flag system
(`packages/server/src/features.ts`), the memory subsystem, and Drizzle/SQLite. No new runtime
dependencies unless noted.

---

## Phase 1 — Lossless context: linktree anchors (replaces lossy compaction)

Problem: summary-based compaction is lossy and becomes the "source of truth", so the agent
forgets the original task and builds on faded anchors.

Design:

- Anchors are **references, not summaries**: every anchor entry links to the original
  un-summarized message/part (`ref:msg_id`) stored in SQLite. The anchor tree is a compact index;
  the DB is the source of truth. Zero information loss.
- `recall_context` tool — the agent fetches any original slice on demand (by anchor, message id,
  or session range).
- `search_memory` tool — SQLite FTS5 index over session content for keyword retrieval.
- Compaction then becomes "build a linktree checkpoint", not "destroy context".

Where it lives: memory subsystem (already feature-flagged), `packages/db` schema for anchor
tables + FTS5 virtual table; `packages/server/src/session/` for the compaction hook swap;
tools registered through the existing tool registry (feature-flag: `memory`).

## Phase 2 — Auto-healing model fallback

Problem: free models run out of limits; the run dies.

- `Effect.Schedule`-driven retry with model rotation: on rate-limit/timeout, fall back to a
  similar-capability model (configurable candidate list, smart default = same tier).
- Retry N times per model, then rotate; if retries keep timing out, trigger a compaction
  checkpoint (Phase 1 linktree) and continue.
- Emits session events so the UI shows "switched to X after limit on Y".

Where: `packages/server/src/session/llm/` (native runtime already exists) — wrap the model call
site with the fallback schedule; per-session config in `llm` config block.

## Phase 3 — Agent self-management: tasks

The agent creates and manages its own work; the human can inject/override at any point
(manual mode = same machinery, human drives).

- Tools: `create_task`, `update_task`, `cancel_task`, `stop_task_llm` (kill the LLM loop but
  keep the task), `revert_task_changes` (git-backed revert of task worktree), plus status/inspect.
- Tasks are **child processes** persisted in SQLite with an `auto_run` flag: after the main agent
  process restarts, marked tasks are re-spawned automatically.
- Event hooks: `on_complete`, `on_fail`, `on_timeout` → run actions (e.g. `notify-send`,
  webhook, another task).
- The main agent can re-point a task's prompt and choose the model/subagent types a task may use.
- The human sees every task in the web UI and can pause/steer — smart default = agent proceeds
  autonomously unless a permission tier requires approval.

Where: `packages/server/src/task/` (new subsystem, feature-flagged `tasks`), SQLite tables via
Drizzle migration, child processes via existing Process util + heartbeat rows.

## Phase 4 — Watchdog + stuck detection

- `packages/server/src/session/watchdog.ts`: fiber watching each run — no progress for N seconds
  or the same tool called M times in a row → interrupt, checkpoint (linktree), restart the loop
  with a self-correction prompt.
- Heartbeat table doubles as the task-watchdog for Phase 3 child processes.

## Phase 5 — Subagent types

- Built-in types: `coder`, `researcher`, `shell`, `reviewer` — per-type system prompt + tool
  allowlist (reuse existing agent/permission definitions).
- The parent agent picks the model per subagent (from allowed list) and the allowed subagent
  types inside tasks.
- Subagent status visible to parent (and UI) via the task/child-process registry.

## Phase 6 — Machine tools (permissions tiered)

New tools so the agent can really use the machine, each behind the existing permission system:

`notify`, `get_system_info`, `list_processes`, `kill_process`, `http_request`, `screenshot`,
`clipboard`, `glob_search`, `watch_file`.

Default tier: read-only/info tools auto-allowed; destructive (`kill_process`, clipboard write,
http_request to non-allowlisted hosts) require permission — configurable per project like
existing tool permissions.

## Phase 7 — Access surfaces: SSH REPL + curl + messaging

- SSH server (`ssh2`) on port 2222 (configurable): real interactive REPL into the agent — a
  minimal CLI (new session, list tasks, tail events, prompt). Not just port forwarding.
- `curl` script endpoint: on-the-fly one-liner to prompt the agent from any device
  (token-authed `POST /api/session` + prompt).
- Discord/Telegram integrations: same event bus the web UI uses; messages become session prompts,
  replies go back to the channel. Feature-flagged.

## Phase 8 — System prompt rewrite (smart by default)

Rewrite system prompts to support autonomy:

- **Objective anchoring**: the original task is restated at every checkpoint from the linktree
  root (never a summary of a summary).
- **Memory instructions**: when to call `recall_context` / `search_memory`.
- **Progress checkpointing**: agent writes anchors at milestones so restarts resume cleanly.
- **Self-correction loop**: on watchdog interrupt, the restart prompt includes what looped/failed.

`packages/server/src/session/prompt.ts` is the current home; keep manual mode identical — the
human's message is just another anchor root.

---

## Sequencing & flags

Order: 1 → 2 → 4 (stability) → 3 (tasks) → 5 → 6 → 7 → 8. Phase 1 is the foundation: without
lossless context, autonomy on small-context free models cannot work.

Feature flags (default on, smart by default): extend `features.ts` with `tasks`, `ssh`, and
per-integration flags; the existing `memory` flag gates Phase 1 tools. Every phase must remain
fully usable in manual mode — autonomy mechanisms are additive fibers/tools, never a mode switch.

## Open questions

- Anchor storage: reuse the memory DB or a dedicated `anchors` table set?
- Task child processes: Bun subprocesses vs in-process Effect fibers behind an API?
- SSH auth: reuse server password or separate host keys + agent token?
